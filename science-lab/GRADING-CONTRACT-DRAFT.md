# GFIELD Science Lab 서술형·자유형 공통 채점 계약 — 승인 대기 초안

작성·참고 반영: 2026-09-25 · 상태: **참고 설계·로컬 수동 학습 UX 도입 승인 / AI 채점·실데이터 연결 승인 대기**

## 1. 범위와 현재 사실

- 웹 타자, 학생·보호자 사진, 강사의 답안지 묶음 촬영은 **같은 채점 계약**으로 들어간다. 종이 답안은 전사 결과를 학생이 확인한 뒤에만 채점한다. 알림·타이머는 만들지 않고 제출 시각만 기록한다.
- 현행 `v2/v2.js`의 `written-explanation`은 답 입력란·예시 답·수동 체크 기준만 제공한다. 자동 채점·실제 QR·사진 전사는 없다. `intro/intro.js`의 빨간 펜·QR·자유형 루브릭은 **광고용 그림**이며 실제 채점 결과가 아니다.
- 기존 서술형 문항의 `answerContract.rubric.required[]`, `pass`, `accepted?`, `bonus?`, `sample`을 기준 자료로 쓴다. 출처가 보호된 단원평가 원문·정답을 git이나 공개 프롬프트 로그에 복사하지 않는다. 자유형은 현재 광고 견본 외에 승인된 문항·루브릭 카탈로그가 없다.
- 이 문서는 **채점 계약만** 정한다. 학생별 QR 인쇄, 처방지 인쇄, 사진 전사·채점 연결은 각각 후속 승인 단계다.
- 사용자의 두 참고 URL 도입 요청에 따라 답안 작성 도움말, 내 답·풀이·채점 기준 구분, 수동 점검의 로컬 개선을 진행한다. 이 요청은 실제 학생 답안의 외부 전송·운영 수집·배포 승인이 아니다. 근거와 도입 상태는 [참고 도입 기록](./REFERENCE-ADOPTION-2026-09-25.md)에 구분한다.

## 2. 단일 파이프라인과 책임 분리

```text
웹 타자 ───────────────────────────────┐
종이/앱 사진 → QR 식별 → 전사 → 학생 확인 ├→ grade(input) → 검증 → 교사 검토/공개 → 고쳐 쓰기 → 재채점 → 진단/처방
강사 묶음 사진 → 장별 분리 → QR 식별 → 전사 → 학생 확인 ┘
```

1. 서버가 로그인·소속·학생 접근권과 QR의 서명을 확인한다. QR에는 이름·연락처·답안·정답을 평문으로 넣지 않는다. QR은 내부에서 `studentId / unit / page / itemId / sheetNo`로 해석되는 서명된 불투명 토큰을 사용한다. 카메라가 읽은 문자열만 믿고 학생을 배정하지 않는다.
2. 사진 전사는 **채점과 별도 단계**다. 흐린 부분을 추측해 확정하지 않고 위치와 후보를 표시한다. 여러 장은 `sheetNo` 중복·누락을 확인해 한 답안으로 묶는다. QR 불일치나 장 누락은 `needs_review`로 멈춘다.
3. 학생이 전사문을 읽고 고치거나 `이대로 채점`을 눌러 확정한다. 확인 전에는 모델 채점·오개념 기록·성적 발송을 하지 않는다. 웹 타자 입력은 제출 확인을 학생 확인으로 본다.
4. `grade(input)`은 **확인된 텍스트**와 승인된 문항·루브릭만 평가한다. 사진 참조는 추적용으로 입력 계약에 남기되, 채점 모델에는 기본적으로 다시 보내지 않는다. 이미지 재확인이 필요한 경우 별도 권한·동의와 검토 단계를 둔다.
5. 모델 출력은 바로 성적으로 쓰지 않는다. 서버가 스키마·점수·근거·문항 일치를 검증하고, 불확실하면 교사 검토 대기 상태로 둔다. 교사 수정 이력을 남기며 이전 결과를 덮어쓰지 않는다.

### 제출 상태와 풀이 공개

- 정상 제출 상태는 `draft → submitted → transcribing → awaiting_student_confirmation → ready_to_grade → grading → graded_draft → published`로 연결한다. 오류·불확실성은 어느 단계에서든 `needs_review`로 보내며, 교사 확인 후 해당 단계로 복귀해야 한다. 검토 대기에서 곧바로 공개하지 않는다. 웹 타자는 전사 단계를 생략한다. 고쳐 쓴 답은 새 `attempt`로 연결하고 이전 답과 결과를 보존한다. 전사 실패·누락·확인 취소를 제출 완료나 0점으로 표시하지 않는다.
- **학습 모드**는 학생이 자기 답을 작성한 뒤 풀이·채점 기준을 직접 펼쳐 비교한다. 수동 체크는 스스로 점검한 기록이며 교사 판정·자동 점수가 아니다.
- **평가 모드**는 과제별 `releasePolicy`에 따라 제출 후 또는 교사 공개 시에만 풀이를 제공한다. 서버가 접근권을 검사하며, 정답을 HTML·클라이언트 번들에 먼저 넣고 화면에서만 숨기는 방식은 평가 보안으로 인정하지 않는다. 현재 정적 학습 화면은 이 평가 모드를 구현한 상태가 아니다.
- 인쇄물 QR, 사진 장 번호, 학생 확인, 교사 검토, 처방·재확인은 동일한 `submissionId` 아래 이력으로 연결한다. 처방 결과를 최초 답안 점수에 덮어쓰지 않는다.

## 3. `grade(input) → output` 계약 v1

### 입력

```ts
type GradeInput = {
  version: '1';
  submissionId: string;               // 재시도 중복 방지용 내부 UUID
  attempt: number;                     // 1차 답=1, 고쳐 쓰기=2 …
  student: { id: string };             // 내부 가명 ID; 이름·연락처는 모델에 전달하지 않음
  unit: string;                        // 예: s41-u03
  type: 'written' | 'free';
  assessmentKind: 'explanation' | 'ideas' | 'design';
  mode: 'learning' | 'assessment';
  item?: string;                       // written: 승인된 창작 문항 ID
  promptId?: string;                   // free: 승인된 주제 카탈로그 ID
  prompt?: string;                     // free: 승인된 주제 카탈로그의 문장
  itemVersion: string;                 // 문항/주제 버전, 제출 시 고정
  images: Array<{ imageId: string; sheetNo: number }>;
  typed?: string;                      // 학생이 확인한 최종 전사문 또는 웹 제출문
  rubricVersion: string;
  releasePolicy: 'after_attempt' | 'after_submission' | 'teacher_release';
};

interface GradeAdapter {
  grade(input: GradeInput): Promise<GradeResult>;
}
```

- `written`은 `item` 필수, `free`는 승인된 `promptId` 필수다. `prompt`는 서버가 해당 ID·버전으로 조회한 문장이다. 둘 중 어느 경로든 서버가 문항과 루브릭, 평가 종류, 공개 정책을 조회한다. 브라우저가 보낸 정답·채점 기준·모드·공개 정책은 신뢰하지 않는다.
- `images[]`는 서버 내부 참조만 담는다. `typed`가 비어 있거나 학생 확인이 안 되었으면 `grade()`를 호출하지 않는다. 모델 요청에는 `student.id`, QR 토큰, 이미지 경로를 넣지 않는다.
- 같은 `submissionId + attempt + itemVersion + rubricVersion`은 멱등하게 처리한다. 재시도는 기존 결과를 반환하거나 검토 상태로 보내며 이중 청구·이중 기록을 막는다.
- `assessmentKind`는 채점자가 답안을 보고 임의 추정하지 않고 문항 등록 시 정한다. `explanation`은 과학 용어·관찰/자료·원인과 결과의 연결, `ideas`는 조건을 만족하는 서로 다른 아이디어, `design`은 해결할 문제·관련 과학 원리·적용 방법을 살핀다. **교수용 점검 관점**이며 모든 입시의 공식 공통 루브릭이라는 뜻이 아니다. 실제 점수는 해당 문항의 승인된 기준만 사용한다.

### 공통 결과와 서술형 결과

```ts
type Common = {
  version: '1';
  submissionId: string;
  attempt: number;
  type: 'written' | 'free';
  status: 'graded_draft';
  provider?: string;                   // 호출했을 때만 서버 저장; 호출 전 검토는 없음
  itemVersion: string;
  rubricVersion: string;
  resultId: string;                    // 결과 이력의 고유 ID
  supersedesResultId?: string;         // 교사 정정/기준 변경 재채점 시 이전 결과
};

type WrittenResult = Common & {
  type: 'written';
  verdict: 'correct' | 'partial' | 'incorrect';
  matched: Array<{ criterion: string; evidence: string }>;
  missing: Array<{ criterion: string; why: string }>;
  explanation: string;                 // 4학년 수준의 짧은 교정 설명
  spelling: Array<{ before: string; after: string; why: string }>;
  criteria: Array<{
    criterion: string;
    state: 'met' | 'partial' | 'not_met';
    earned: number;                    // 승인된 부분점수 규칙에 따라 서버 확정
    max: number;                       // 원문/교사 승인 배점, 임의 균등 배분 금지
    evidence: string[];
    ruleIds: string[];                 // 적용한 승인 규칙/점수 상한 ID
    why: string;
  }>;
  score: { earned: number; max: number }; // 원문 배점 보존; 서버가 규칙에 따라 합산
  normalizedScore?: { earned: number; max: 5 }; // 승인된 보고서 환산이 있을 때만 별도 표시
  misconceptionCandidates: string[];  // 해당 단원에 등록된 M 코드만, 확정 진단 아님
};
```

- `matched[].criterion`과 `missing[].criterion`은 문항의 `rubric.required[]`를 안정적인 ID로 변환한 값이다. 모델이 새 기준을 만들어 추가할 수 없다. 각 `evidence`는 **확인된 학생 답안에 실제로 있는 표현**이어야 한다.
- 학생이 다른 말로 정확히 설명해도 맞게 본다. `rubric.accepted`가 있으면 동등한 설명의 예로만 쓰고 유일한 정답 표현으로 강제하지 않는다. 핵심 사실과 반대되는 문장이 있으면 단순 키워드 포함만으로 정답 처리하지 않는다.
- 맞춤법은 과학 개념과 분리한다. 개념이 맞고 철자만 틀렸다면 서술형 개념 점수를 임의 감점하지 않는다. 증거가 부족하거나 서로 모순되는 답, 읽기 어려운 답은 `needs_review`다.
- **원문 배점 보존**: 문항·소문항·기준별 원래 배점과 총점을 유지한다. 현행 `required/pass`만 있고 수치 배점·부분점수 규칙이 없는 문항에는 균등 배점이나 기본 5점을 만들어 적용하지 않는다. 해당 문항은 수동 체크·교사 검토로 남기며 자동 채점 호출은 `needs_review` 사유 `rubric`로 종료한다.
- 루브릭은 기준별 만점, 허용 부분점수, 인정 근거, 점수 상한, 적용 우선순위, 정오 판정 규칙을 명시한다. 답만 맞고 필요한 과정이 없는 경우에도 **승인된 규칙이 있을 때만** 점수를 제한한다. `bonus`는 승인된 수치 규칙이 없으면 칭찬 피드백으로만 쓴다.
- 점수는 기준별 획득점수를 합산하고 승인된 상한을 적용한다. 같은 누락을 기준 미충족과 별도 감점으로 두 번 차감하지 않는다. 상충하는 규칙, 설명되지 않는 총점, 원래 총점과 기준 배점 합계의 불일치는 교사 검토 대상으로 둔다.
- 보고서용 5점 환산을 승인하면 원점수/원만점을 함께 보존하고 별도 필드에 환산한다. 반올림 단위 역시 보고서 정책에 명시하며, 환산값으로 원문 점수나 정오 판정을 덮어쓰지 않는다.

### 자유형 결과

```ts
type FreeResult = Common & {
  type: 'free';
  rubric: Array<{
    k: '내용' | '구성' | '표현' | '맞춤법';
    score: number;                     // 각 정수 0~5
    why: string;                       // 학생 글의 실제 부분을 근거로 설명
  }>;
  rewrite: string;                     // 전체 대필이 아닌 고쳐 쓸 문장 1개
  words: string[];                     // 학년 맞춤 낱말 제안, 최대 4개
  spelling: Array<{ before: string; after: string; why: string }>;
  misconceptionCandidates: string[];  // 과학 개념이 명백할 때만, 확정 진단 아님
};

type ReviewResult = Omit<Common, 'status'> & {
  status: 'needs_review';
  reasonCode: 'transcription' | 'identity' | 'rubric' | 'model' | 'conflict' | 'schema';
};

type GradeResult = WrittenResult | FreeResult | ReviewResult;
```

- 네 기준은 각각 5점, 합계 20점이다. 합계는 **서버가 계산**한다. 교사 승인 자유형 문항·루브릭이 없으면 점수를 내지 않고 `needs_review`로 보낸다.
- 모델은 학생의 목소리를 지우는 완성 글을 대필하지 않는다. `rewrite`는 한 문장의 수정 예시이고, `words[]`는 학생 수준에 맞는 낱말만 제안한다. 자유형 답안이 교과 사실을 다뤄도 루브릭 점수와 과학 오개념 후보를 분리한다.
- `assessmentKind`는 위 네 영역을 대체하거나 점수를 추가하지 않는다. 설명·아이디어·설계에 맞는 관찰 항목을 해당 문항의 `내용/구성/표현` 수준 설명에 반영한다. 서로 같은 뜻을 반복한 아이디어는 별개의 아이디어로 중복 집계하지 않되, 애매한 유사성은 교사가 판단한다.
- 창의성의 유창성·다양성·독창성은 수업 피드백의 참고 관점이다. 이 계약은 자동 희귀도 점수·독창성 순위·영재 여부·입시 합격 가능성을 산출하지 않는다. 아이디어 수만으로 창의성 점수를 대체하지 않는다.

## 4. Gemini 어댑터, 검증, 실패 처리

- 기본 어댑터는 서버 측 `GeminiGradeAdapter`; 같은 `GradeAdapter` 계약을 지키는 다른 공급자로 교체 가능하다. API 키는 서버 비밀값으로만 보관하고 브라우저·QR·git에 넣지 않는다. 모델명·SDK 버전은 **구현 시 공식 문서 재확인 후 고정**한다.
- Gemini의 JSON Schema 기반 구조화 출력을 사용하되, 구조화 출력만으로 내용의 타당성이 보장되지는 않는다. 서버가 허용된 필드·코드·기준 ID, 점수 범위, 중복 기준, 근거의 답안 내 존재 여부, `criteria`의 모든 기준 1회 포함, 적용 규칙·부분점수·총점·판정의 일관성을 별도로 검사한다. `matched/missing`은 기준별 상태의 설명으로 검증하며 부분 충족을 완전 충족으로 바꾸지 않는다.
- 잘못된 JSON, 안전 필터 차단, 시간 초과, 루브릭 버전 불일치, 낮은 전사 확신도, 상충하는 사실 판단은 **점수 0이 아니라 `needs_review`**다. 자동 재시도는 같은 입력·버전에서 최대 1회만 제안하며, 계속 실패하면 교사에게 넘긴다.
- 모델은 처음부터 오개념 코드를 자유 생성하지 않는다. 서버가 해당 단원 `*.misc.js`의 후보 목록을 제한적으로 제공하고, 문장 근거가 있는 후보만 받아들인다. 한 문항의 1차 답·고쳐 쓰기는 서로 다른 확인 문항으로 세지 않는다. 기존 진단의 `의심 → 확정(서로 다른 문항 2개) → 해소` 규칙을 유지한다.
- 교사에게는 원문 답안, 학생 확정 전사문, 기준별 근거, 모델/루브릭 버전, 교사 수정 전후 결과를 비교할 수 있게 한다. 학생에게는 점수보다 **맞은 생각·빠진 생각·다음에 해 볼 일**을 먼저 보여 준다.

### 문항·루브릭 버전과 재채점

- 제출 시 문항/주제·루브릭의 ID와 버전을 함께 고정한다. 최신 정오표의 자료로 다시 열더라도 기존 제출의 평가 근거는 바꾸지 않는다.
- 문구 정리와 정답/배점 변경을 구분해 수정 일자·이유·영향 문항을 기록한다. 정답/배점 변경은 교사가 재채점 대상을 검토하고 승인한 후 실행한다.
- 같은 답을 새 기준으로 다시 채점할 때는 학생의 새 풀이 `attempt`로 세지 않고 새 `resultId`와 이전 결과 참조를 남긴다. 학생이 고쳐 쓴 경우만 새 `attempt`다. 과거 결과·교사 조정·공개 시각·점수 변경 사유를 보존한다.
- 재시도, 동일 답의 기준 변경 재채점, 교사 수정은 새 확인 문항이 아니다. 기존 오개념 진단의 서로 다른 문항 2개 조건에 중복 증거로 넣지 않는다.

## 5. 개인정보·원문 경계 (구현 전 필수 확인)

- 현재 Gemini 약관상 **무료 서비스에는 개인정보나 민감정보를 보내지 말아야 한다**. 따라서 실제 학생 사진·답안은 무료 Gemini 호출 대상이 아니다. 유료 프로젝트 이용 시에도 데이터 처리·보관·국외 처리와 보호자/기관 동의를 별도로 검토해야 한다. 무료 호출은 가상 학생·자체 작성 답안의 개발 테스트로만 제한한다.
- 서버에는 최소 가명 ID와 채점에 필요한 확인된 텍스트만 전달한다. 얼굴, 이름표, 전화번호 등 불필요한 부분은 사진 전 단계에서 가리거나 촬영 안내로 배제한다. 원본 사진·전사문·채점 기록은 비공개 저장, 최소 권한, 학생/교사 소속 검증, 보존 기간·삭제 절차가 확정되기 전에는 운영 데이터를 수집하지 않는다.
- Supabase 사용 시 답안 테이블은 노출 스키마의 RLS와 소유/소속 정책을 함께 검증한다. Storage는 공개 버킷이 아닌 비공개 접근으로 설계한다. `service_role`/secret 키를 클라이언트에 두지 않는다. 원문 문제은행과 학생 답안의 접근권·로그를 섞지 않는다.
- 기존 Report3 파이프라인 재사용 가능성은 **설계 가정**이다. 실제 저장소의 권한·로그·보존 정책·비용·전사 품질을 확인하기 전까지 연결 완료로 표시하지 않는다.

## 6. 승인 후 순서와 검수 게이트

1. **이 계약 승인**: 점수 규칙, 학생 확인 방식, 실제 학생 데이터의 공급자·비용·동의, 보존 기간을 결정한다.
2. 학생별 QR 인쇄: 실제 읽히는 QR, 서명/권한/장 번호 검사, 원고지 칸, A4와 390px 미리보기. 잘못된 QR은 다른 학생 답안으로 들어가지 않아야 한다.
3. `#/<단원>/remedy/print`: 기존 진단에서 처방 한 장을 만들고, 이 단계에는 AI 호출을 넣지 않는다.
4. 사진 전사·학생 확인·채점: 가상 답안으로 먼저 테스트한 뒤 별도 실데이터 승인. 흐림·누락·중복 장·QR 바꿔치기·모델 실패·교사 수정·재채점 시나리오를 검사한다.
5. 교사 검수용 표본에서 정답·동의어·부분 정답·과학적 모순·맞춤법만 틀림·자유형 4영역을 독립 채점과 대조한다. 배점 없는 문항의 자동 채점 중단, 중복 감점 방지, 반복 아이디어, 문항/루브릭 변경 재채점, 평가 풀이의 조기 노출도 검사한다. 합격 기준과 출시 여부는 표본을 본 뒤 원장이 정한다.
