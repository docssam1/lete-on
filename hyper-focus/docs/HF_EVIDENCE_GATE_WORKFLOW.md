# Hyper Focus 근거·단일정답·풀이 장면 작업 계약

이 문서는 Hyper Focus의 새 문항, 변형 문제, 모의고사 연결, 진단, 향후 절차형 풀이를 만들거나
고칠 때 적용하는 전용 작업 규칙이다. 다음 두 스킬에서 Hyper Focus에 필요한 부분만 결합한다.

- `skills/concept-whiteboard-lesson/SKILL.md`
- `evidence-gated-learning-pipeline`:
  `https://github.com/docssam1/source-to-memory/tree/main/skill/evidence-gated-learning-pipeline`

모든 기존 문제를 애니메이션으로 바꾸는 문서가 아니다. 풀이 순서 자체가 학습 내용인 경우에만
화이트보드 장면을 사용한다. 일반 변형 문제와 PDF 페이지 이미지 모의고사에는 근거, 정답 계약,
관찰 가능성, 학습자 적합성, 화면·인쇄, 공개 관문만 적용한다.

## 1. 범위와 권한

- 수정 범위는 `hyper-focus/**`뿐이다.
- 황소 초등·중등, 필즈 더 클래식, 고등 선발, Geometry 등은 읽기 전용 참고다.
- 공용 루트 파일 수정, `main` 병합, 운영 배포, 실제 학생 생성·삭제는 각각 별도 사용자 승인 대상이다.
- 원본 PDF·답안·대본·학생 정보·비밀 키·개인 절대경로를 공개 Git 문서나 공개 manifest에 넣지 않는다.
- 테스트 통과는 공개 승인이 아니다. 구현자가 자신의 결과를 단독으로 최종 승인하지 않는다.

## 2. 작업 시작 계약

코드나 데이터를 바꾸기 전에 작업 단위별로 다음을 기록한다.

```text
workKey:
objective:
learnerStage: 7~8세
difficulty: 쉬움 | 같게 | 어려움
learnerAction: 계산 | 세기 | 고르기 | 그리기 | 접기 | 회전 | 설명
sourceRecordIds:
sourceLocators:
exclusions:
authorizedPaths: hyper-focus/** 안의 정확한 파일 목록
answerContract: single-value | ordered | set | range | rubric | provisional
releaseAuthority:
doneWhen:
verificationCommands:
```

`workKey`는 재개해도 바뀌지 않는 키를 쓴다.

- Hyper Focus 변형: `hf:qNN:var01` 또는 `hf:qNN:var02`
- 생성형 난이도: `hf:qNN:easy`, `hf:qNN:same`, `hf:qNN:hard`
- 프리미어 문항: `premier:{series}-{round}:qNN:r{revision}`
- 절차형 풀이: 위 키 뒤에 `:lesson`을 붙인다.

## 3. 먼저 찾고, 근거 순서를 지킨다

새 생성기·계산기·렌더러를 만들기 전에 다음을 순서대로 찾는다.

1. 현재 브랜치, Git 상태, 최근 커밋과 이 인수인계 문서를 확인한다.
2. `canonical`, `variations`, 기존 generator, renderer, QA, tests에서 같은 유형과 별칭을 찾는다.
3. `.source-memory`가 있으면 원본 본문이 아니라 record ID·fingerprint·locator를 조회한다.
4. 계약이 같은 기존 계산기와 렌더러를 재사용한다. 이름만 다른 복제 구현을 만들지 않는다.
5. 기존 구현이 원본 구조와 다르면 연결하지 않고 `conflict` 또는 `locked`로 기록한다.

근거 신뢰 순서는 다음과 같다.

1. 결정적 자동 검사와 독립 계산 결과
2. 정확한 fingerprint와 원본 위치 locator
3. 사용자가 승인한 명시적 사양
4. 최신 인수인계서
5. OCR, 파일명, 영상 대본, 채팅의 불완전한 힌트

낮은 순위 근거만으로 답이나 유형을 확정하지 않는다. 원본이 바뀌면 해당 원본에 의존하는 근거를
`stale`로 바꾸고 공개 상태를 다시 `locked`로 돌린다.

## 4. 세 상태를 분리한다

한 단어로 작업 완료, 근거 확인, 공개 승인을 섞지 않는다.

- 작업 상태: `pending`, `in-progress`, `complete`, `blocked`
- 근거 상태: `draft`, `verified`, `conflict`, `stale`, `superseded`, `excluded`
- 공개 상태: `locked`, `eligible`, `approved`, `published`, `revoked`

현재 앱의 `releaseStatus`와는 다음처럼 해석한다.

- `locked`, `review_pending`: 파이프라인 공개 상태 `locked`
- `verified`: 필수 관문을 통과한 `eligible`이며 사용자 공개 승인과 다르다.
- `published`: 사용자 승인, 원격 반영, 실제 배포 readback까지 끝난 경우에만 사용한다.

반복 작업을 실제로 시작할 때만 `.evidence-pipeline/pipeline.json`에 해당 `workKey`를 추가한다.
빈 항목을 54개 또는 300개처럼 미리 대량 생성하지 않는다. ledger에는 원본 내용과 개인 경로 대신
record ID, fingerprint, 안전한 locator, 검사 이름, 캡처 ID, 결정 위치만 기록한다.

## 5. 수학·단일정답 계약

문항마다 먼저 답의 형식을 고정한다.

- `single-value`: 숫자나 선택지 하나
- `ordered`: 순서가 다른 답을 서로 다르게 채점
- `set`: 순서를 무시한 허용 답 집합
- `range`: 최솟값·최댓값 또는 범위
- `rubric`: 그림·작도·설명형의 허용 조건 판정
- `provisional`: 원본이나 조건이 부족해 아직 공개할 수 없는 임시 판단

필수 규칙:

- 생성기가 만든 `answer`를 그대로 다시 읽어 정답 검산으로 삼지 않는다.
- 독립 계산 또는 가능한 답의 전체 열거를 사용한다.
- 단답형은 유효 후보가 정확히 하나일 때만 통과한다.
- 결정 가능성(조건으로 답이 하나인가)과 관찰 가능성(그림에서 필요한 정보가 보이는가)을 따로 검사한다.
- 복수답, 숨은 블록, 모호한 시선, 접기축·회전 기준 누락은 설명으로 덮지 않고 잠근다.
- 실패한 문항은 기존 자료 전체를 폐기하지 않는다. 해당 revision만 `excluded` 또는 `superseded`로 남기고,
  새 revision이 독립 검증을 통과할 때까지 공개하지 않는다.

Hyper Focus 변형은 반드시 `canonical/qNN.json`의 `solvingModel`, 원본 문제 그림, 변형의 문제 문장,
그림, 정답을 1:1로 대조한다. 숫자를 바꿀 수 있어도 문제 구조·시점·질문·답 형식은 바꾸지 않는다.

## 6. 7~8세 learner-fit 관문

모든 학습자용 문항은 아래 다섯 기준을 각각 기록해야 한다. “아이에게 적절함” 한 줄로 통과시키지 않는다.

| 기준 | Hyper Focus 통과 조건 |
|---|---|
| `language` | 7~8세가 읽을 수 있는 짧은 문장이고 순열·조합·제곱·비례식 같은 학년 밖 용어를 쓰지 않음 |
| `representations` | 칸, 수 그림, 바탕그림, 접기선, 시선 표시가 문제의 실제 추론을 도우며 답을 미리 노출하지 않음 |
| `prerequisites` | 문제에서 요구하는 사전 개념이 해당 연령이 배운 방법 또는 화면에서 설명한 방법 안에 있음 |
| `reasoning-load` | 쉬움 < 같게 < 어려움이 조건 수, 추론 단계, 표현 전환, 오답 유사도에서 실제로 구분됨 |
| `response-mode` | 숫자, 선택지, 순서, 그림 중 아이가 해야 할 응답과 채점 방식이 일치함 |

조사와 단위 표현은 생성된 숫자를 넣은 최종 문장으로 검사한다. 난이도는 숫자 크기만 올려 만들지 않는다.

## 7. 절차형 풀이에만 화이트보드를 쓴다

다음처럼 **순서가 풀이 내용인 경우**에만 `concept-whiteboard-lesson`을 적용한다.

- 위에서 본 바탕그림의 각 칸에 높이를 하나씩 쓰고 더하기
- 색종이를 접은 순서의 반대로 펼치며 구멍 위치 찾기
- 주사위를 한 칸씩 굴리며 면 추적하기
- 카드 교환이나 사람 이동을 마지막 상태에서 거꾸로 복원하기

정적 정의, 단순 정답 확인, 완성 그림만 보면 되는 문항에는 적용하지 않는다.

절차형 장면 계약:

1. 생성기의 의미 데이터에서 장면을 만든다. TeX나 화면 문장을 다시 파싱해 수를 복원하지 않는다.
2. 기존 반환값·정답·인쇄물을 바꾸지 않는 additive `scene:{}`와 안정된 object ID를 사용한다.
3. `steps`가 실제 풀이 순서이고, 한 beat에는 새 대상 하나만 나타난다.
4. 좌표는 점·선·칸·면·블록·접기축 모델에서 계산한다. 눈대중 SVG 좌표를 답 근거로 삼지 않는다.
5. 이미 만든 대상을 다시 볼 때만 `highlight`를 쓰고 다음 beat에서 지운다.
6. 화면의 `풀이 보기`는 첫 오답 1회 뒤에만 연다. 인쇄물은 별도 정답·풀이 면을 사용한다.
7. 재생, 일시정지, 처음부터, 속도, 자막, 모션 축소를 제공한다.
8. 음성은 선택 기능이다. 현재 제공 언어마다 자막을 직접 작성하고, 소리가 없어도 이해되어야 한다.
9. 마지막 정지 장면은 A4에 그대로 인쇄해도 풀이 순서가 이해되어야 한다.

## 8. 산출물별 필수 관문

| 관문 ID | 확인 방법 | 통과 조건 |
|---|---|---|
| `source-scope` | 원본 locator·사용자 결정 대조 | 구조, 조건, 시점, 질문, 답 형식 일치 |
| `math-model` | 독립 계산·불변식 검사 | 의미 모델이 조건과 답을 정확히 표현 |
| `answer-contract` | 가능한 답 전체 열거 | 단일답 1개 또는 명시된 집합·범위·rubric과 일치 |
| `observability` | 시선·가림·색·선 검사 | 화면에 보이는 정보만으로 계약된 답에 도달 |
| `learner-fit` | 다섯 기준 별도 기록 | 7~8세 언어·표현·선수지식·추론량·응답 적합 |
| `variation-diversity` | var01/var02 및 난수 표본 비교 | 정답과 표면 수치가 의미 있게 다양하고 구조는 동일 |
| `scene-data` | 생성 데이터와 장면 object·beat 대조 | 절차형 풀이의 수·좌표·순서가 생성 결과와 일치 |
| `gaze` | beat별 실제 캡처 육안 검사 | 절차형 풀이에서 매 beat 새 초점 하나 |
| `render-pc` | 실제 데스크톱 브라우저 | 잘림, 겹침, 빈 그림, 정답 노출 없음 |
| `render-mobile` | 390px와 실제 모바일 조작 | 가로 넘침 없고 글자·그림·터치가 분명함 |
| `render-a4` | 실제 PDF와 페이지 이미지 | 여백, 필기 공간, 페이지 분리, 최종 장면 정상 |
| `accessibility` | 키보드·텍스트·색상 검사 | 색·음성·동작만으로 의미를 전달하지 않음 |
| `negative-control` | 핵심 검사 대상을 일부러 깨고 재실행 | 검사가 실제 실패한 뒤 원복됨 |
| `regression` | 관련 QA·tests 전체 재실행 | 기존 승인번호·진단·모의고사·인쇄 계약 유지 |
| `privacy-delivery` | manifest·RLS·서명 URL·직접 URL 검사 | 비공개 원본·답안이 공개 Git/URL에 없고 권한 없는 접근 차단 |
| `release-readback` | 원격 SHA·Actions·실제 URL 확인 | 사용자 승인된 같은 SHA가 실제 배포 화면에 반영 |

해당 산출물에 적용되는 관문은 `pass`, `fail`, `blocked`, `pending`으로 기록한다. 적용되지 않는 관문은
근거 상태 `excluded`와 이유를 적는다. 필수 관문 하나라도 `pass`가 아니면 완료 또는 공개라고 말하지 않는다.

모의고사 페이지 이미지에는 `scene-data`와 `gaze`를 적용하지 않는다. 대신 원본 페이지 순서,
페이지별 fingerprint, 모바일 확대, A4 재인쇄, private Storage 전달을 필수로 한다. 일반 변형 문제에는
절차형 풀이를 실제로 추가하지 않는 한 장면 관문을 적용하지 않는다.

## 9. Negative control

검사가 초록색이라는 사실만으로는 부족하다. 작업 종류에 맞는 핵심 검사를 한 번씩 고의로 깨고 실패를
확인한 뒤 즉시 원복한다.

- 답 후보를 하나 더 허용해 단일정답 검사를 실패시킨다.
- 시선 코드나 높이 하나를 바꿔 그림-모델 일치 검사를 실패시킨다.
- `viewBox` 또는 카드 폭을 줄여 모바일 잘림 검사를 실패시킨다.
- 절차형 beat에 새 대상 두 개를 넣어 gaze 검사를 실패시킨다.
- 보호 manifest의 fingerprint를 바꿔 무결성 검사를 실패시킨다.
- 권한 없는 회차를 열어 RLS/잠금 검사가 거부하는지 확인한다.

깨진 상태의 파일·데이터·권한은 커밋하거나 운영에 남기지 않는다. 보고서에는 무엇을 깨뜨렸고 어떤
검사가 실패했으며 어떻게 원복했는지 기록한다.

## 10. 모델과 추론 강도

- **SOL + 높음**: 원본 대조, 수학 정답, 단일해, 시점·조건 의미, 잠금/공개 판단
- **SOL + 울트라**: 복잡한 시각 모호성, 큰 후보 공간 전수검사, 상충 근거 해결처럼 꼭 필요한 경우만
- **TERRA + 중간~높음**: 여러 Hyper Focus 파일 연결, 기존 승인번호·진단·보안 기능 보존, 회귀 수정
- **LUNA + 중간**: 범위가 고정된 반복 열거, 렌더 캡처, 형식·문구 점검

낮은 모델이 불확실한 답이나 공개 판단을 스스로 승인하지 않는다. 구현과 정답 검수는 가능한 한 다른
계산 방법으로 분리한다. 울트라는 기본값이 아니며, SOL + 높음으로 해결할 수 없는 고위험 모호성에만 쓴다.

## 11. 체크포인트와 완료 보고

토큰이나 시간이 부족해지기 전에 현재 인수인계서에 다음을 갱신한다.

- 정확한 저장소, 브랜치, HEAD, upstream SHA, 미커밋 여부
- 작업 계약과 수정/제외 범위
- 출처 record ID, fingerprint, locator, 근거 상태
- 관문별 증거와 실패·원복한 negative control
- `pending`, `locked`, `excluded`, `superseded` 항목과 이유
- 다음 한 가지 작업과 정확한 검증 명령
- 수행한 외부 변경과 아직 필요한 사용자 승인

완료 보고 형식:

```text
workKey:
완료한 Hyper Focus 파일/기능:
```
