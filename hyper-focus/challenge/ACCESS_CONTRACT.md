# 2026년 9월 챌린지 대비 · 승인 관리

## 현재 상태

Hyper Focus의 기존 학생 계정·권한 표·관리 RPC를 사용하는 **로컬 승인 관리 기반**이다. 별도 학생 계정이나 별도 승인번호 체계를 만들지 않는다. 실제 서버 배포, 마이그레이션 적용, 실제 학생 승인 변경은 수행하지 않았다.

첫 화면 선택 배너 메타데이터는 하이퍼 포커스 / 프리미어 모의고사 / 챌린지 대비의 세 갈래다. 챌린지는 `hyper-focus/challenge` 경로와 기존 HF 인증 아래 연결된다. 상위 수준이라는 뜻이나 연령 수식어를 붙이지 않는다. 정식 명칭은 ‘2026년 9월 챌린지 대비’다. 기존 `products`와 Hyper Focus·프리미어·VIP 권한은 변경하지 않는다.

## 승인 단위

| 자료 | 정확한 권한 키 | 개수 |
| --- | --- | --- |
| 개념 교재 | `challenge-concept-1`, `challenge-concept-2` | 2 |
| 모의고사 | `challenge-mock-1` ~ `challenge-mock-4` | 4 |
| 회차별 유형 문제은행 | `challenge-bank-` + 원본 `typeId` | 104 |

총 110개. 클라이언트 공개 카탈로그, 서버 고정 허용 목록, SQL 추가 카탈로그를 검사하여 일치시킨다. 와일드카드·임의 유형 이름·기존 `hyperfocus` 권한은 새 함수에서 승인할 수 없다. 동작이 같은 인지 유형이어도 회차의 원본 유형을 독립 선택하도록 기존 `typeId`를 유지한다. 생성 가능/검산 완료 여부는 문제은행이 별도로 확인한다. 승인되었다는 이유로 미검수 유형을 생성 가능으로 바꾸지 않는다.

기존 Hyper Focus의 54유형 엔진과 포괄 승인은 보존한다. 기존 학생을 세부 권한으로 자동 전환하거나 기존 권한을 회수하지 않는다. 54유형 개별 승인 구현과 로컬 검수는 `../TYPE_ACCESS_CONTRACT.md`에 따르며, 실제 서버 적용은 별도다.

## 관리자 흐름

기존 `hyper-focus/admin.html`의 연결 → `challenge/admin.html` → 기존 관리자 로그인 → 학생 목록 불러오기 → 기존 학생 선택 → 개념/회차/유형 체크 → **변경한 항목만 저장**.

- 학생 목록은 기존 `admin-students`의 `list` 응답만 사용한다. 이름으로 새 계정을 만들어 대신하지 않는다.
- 유형은 회차·영역·이름으로 필터링하며 필터 변경이 선택을 해제하지 않는다.
- 저장은 `challenge-access`에 정확히 한 권한씩 요청한다. 새 함수가 서버에서 관리자·현재 직원 상태·대상 학생·정확한 키를 검증한 뒤 기존 `hf_set_student_entitlement`를 호출한다.
- 일부 요청 실패 시 완료 개수를 표시하고 미저장 변경을 남긴다. 성공한 변경만 현재 목록에 반영한다. 일괄 저장을 원자적 트랜잭션으로 주장하지 않는다.
- localStorage 승인, 가짜 로컬 학생 승인, URL 역할 우회는 없다. 관리자 화면에는 문제/정답 데이터 스크립트를 로드하지 않는다.
- 로그아웃·인증 변경·토큰 만료 시 학생 목록/이름/선택을 즉시 지우고 늦게 도착한 이전 응답을 버린다.

## 서버 신뢰 경계

`supabase/functions/challenge-access/index.ts`는 기존 SDK와 같은 `@supabase/supabase-js@2.112.3`를 고정한다. `auth.getUser(token)`로 서버 검증한 사용자만 처리한다. `user_metadata`는 권한 판단에 쓰지 않는다.

`self`는 호출자 자신의 활성 학생 프로필만 읽는다. 호출자 권한의 RLS 읽기를 사용하므로 기존 `hf_private.is_active_student()`의 살아 있는 Auth 세션·계정 활성 상태·로그인 버전·인증정보 변경 검사를 따른다. 다른 학생 ID를 입력받지 않는다. 기존 `hf_entitlements`에서 미시작·만료·회수·챌린지 밖 키를 제외한다.

관리 `set`은 최신 Auth 사용자와 JWT 양쪽의 관리자 역할을 확인한 뒤, 서버 전용 클라이언트로 활성 `hf_admin_accounts`와 인가 변경 시각을 확인한다. 통합 관리자 화면과 동일하게 정상 비밀번호 로그인 세션을 허용한다. 확인된 관리자만 서버 전용 클라이언트로 기존 RPC에 전달하며 서비스 키는 HTML/JS 응답에 포함하지 않는다.

요청은 허용 출처·POST·JSON·4KB·정확한 필드 집합으로 제한한다. 비활성 학생에게 신규 승인하지 않는다. 회수는 서버에서 허용한다. 서버 오류가 나면 허용하지 않는다.

마이그레이션 `20260908222618_challenge_permission_catalog.sql`은 CLI `migration new`로 생성한 파일에 **카탈로그 INSERT만** 추가했다. 학생 권한 변경, 테이블 변경, RLS 완화, RPC 재정의가 없다. 실제 DB에서 검증 쿼리나 migration apply를 실행하지 않았으므로 운영 검증은 미완료다.

## 클라이언트 API와 워터마크

스크립트 순서: 기존 `supabase-config.js` / `supabase-client.js` → `challenge/access-catalog.js` → `challenge/access-service.js`.

- `await HFChallengeAccess.refresh()` — 서버 검증 상태를 메모리에만 받는다. 유효기간은 최대 60초 및 JWT/개별 승인 만료시각 이내다. 아직 유효한 상태는 재확인 중에도 유지하며, 실패하면 즉시 버린다. 동시에 요청하면 진행 중인 요청 하나를 공유한다.
- `allow('challenge-concept-1')`, `allow('challenge-mock-2')`, `allow('challenge-bank', sourceTypeId)` — 동기형, 기본 false. 정확한 승인과 비공개 제공 준비 상태가 모두 필요하다.
- `watermarkIdentity()` — `{studentId,name}` 또는 null. 서버의 활성 프로필과 챌린지 승인에서 확인된 이름만 반환한다.
- `approvedStudentName()` — 위 이름 또는 빈 문자열. 입력칸·URL·localStorage 이름은 사용하지 않는다. 반환 이름을 화면에 넣을 때는 textContent/이스케이프를 사용한다.
- `hfchallengeaccesschange` — 최초 검증 성공(`verified`), 학생 ID/승인 이름 변경(`identity-changed`), 승인 목록/비공개 제공 상태 변경(`permissions-changed`), 실패(`verification-failed`), 인증 변경(`session-changed`), 만료(`expired`), 명시적 초기화(`cleared`) 때 발생한다. 같은 학생·이름·권한 집합·제공 상태로 갱신되면 이벤트를 발생시키지 않아 학습 중 진단과 학습지를 보존한다. 단순 갱신 시작도 화면을 지우지 않는다. 소비 화면은 변경 이벤트에서 허용되지 않은 문제·정답·개인정보를 즉시 지워야 한다. 인쇄 직전에도 재검증한다.
- 자동 갱신 — 60초 승인 응답은 약 45초 뒤 `self` 읽기로 다시 확인한다. 짧은 유효기간은 남은 시간의 75%에 갱신하되 최소 1초 간격이며, 원래 만료 전 갱신할 수 없는 경우 그대로 만료시킨다. 서버에서 새 유효기간을 받기 전에는 기존 만료시각을 연장하지 않는다. `status().refreshAt`은 다음 예정 시각 또는 null이다.
- 정상 `TOKEN_REFRESHED`는 기존 유효기간 안에서 화면을 유지하며 서버를 재확인한다. 동일 승인 응답이면 조용히 갱신하고, 실패·학생 변경·승인 변경은 위와 같이 처리한다. `SIGNED_OUT`, `SIGNED_IN`, `USER_UPDATED`는 이전 학생 정보를 즉시 초기화한다.
- 갱신 실패·로그아웃·만료는 즉시 상태와 두 타이머를 제거한다. 갱신 중에도 기존 만료 타이머는 유지되며, 만료나 인증 변경 후 늦게 도착한 응답은 접근을 되살리지 못한다. 회수는 다음 서버 재확인에서 감지한 즉시 해당 키를 차단한다. 이는 서버 푸시가 아니므로 원격 회수 시각과 브라우저 반영 사이에 다음 확인까지의 시간이 있을 수 있다.
- 로컬 검토는 정확한 localhost/127.0.0.1 주소에서 `?teacherPreview=1`일 때만 허용한다. 운영 도메인과 `file:`은 우회되지 않는다. 로컬 검토는 학생 승인 이름을 만들지 않으며 ‘교사용 검토’로만 표시한다.

개념 교재·모의고사·문제은행의 문제 및 답안 모든 페이지에 **서버 확인 학생 이름 + GFIELD / LETE-ON 워터마크**를 소비 화면에서 적용해야 한다. 이번 모듈은 신뢰할 이름을 제공한다. 실제 모든 출력면의 배치/가림/누락은 출력 검수의 별도 책임이며 승인 모듈 검사로 대체하지 않는다.

## 출시 보류 조건 — 중요

교사용 작업 폴더의 정적 JS와 이미지/PDF 안에는 문제와 답안이 들어 있다. **작업 폴더 전체를 공개 호스팅하면 안 된다.** 새 패키징 도구는 공개 화면과 비공개 문항 파일을 분리하며, 학생 화면은 `challenge-content` 서버에 승인된 자료의 문제/답안을 각각 요청한다. 실제 생성 묶음과 합성 인증을 사용한 화면 검수를 통과했으나 운영 서버 적용 증명은 아니다. 자세한 파일·해시·분할 계약은 `CHALLENGE_PRIVATE_DELIVERY.md`에 있다.

새 서버의 `CHALLENGE_PRIVATE_DELIVERY_READY`는 기본 false이며 학생용 `allow()`도 차단된다. 다음을 모두 확인하기 전에는 이 값을 true로 설정하거나 학생용으로 공개하지 않는다.

1. 정적 원문/답안 JS·JSON·이미지·PDF의 공개 호스팅 제외 또는 직접 URL 접근 거부를 확인한다. 기존 빌드 출력과 이전 URL도 포함한다.
2. 권한을 서버에서 확인한 비공개 문제/답안 제공 경로를 연결하고, 승인 없는 동일 URL/유형 접근을 실제 계정으로 거부하는지 확인한다. 문제만 볼 때 답안이 내려오지 않아야 한다.
3. 마이그레이션과 새 함수 배포, 운영 RLS의 세션 회수·학생 간 접근·관리자 역할 축소·만료 검사를 실제 서버에서 수행한다.
4. 모든 학습/답안 출력면의 서버 확인 이름 워터마크와 권한 만료 후 화면 제거를 검수한다.
