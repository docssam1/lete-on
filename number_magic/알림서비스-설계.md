# 알림톡·문자 서비스 설계 메모 (차후 구현)

> 2026-09-01 원장: "차후 알림톡이나 문자 서비스를 할 거야" — 착수 전 준비 메모.
> 아직 구현하지 않는다. 구현 세션은 이 문서부터 읽을 것.

## 1. 무엇을 보낼 수 있나 (콘텐츠는 이미 준비돼 있다)

앱이 이미 만들고 있는 것들이 그대로 메시지 소재가 된다:
| 메시지 | 데이터 출처 |
|---|---|
| 주간 학습지 도착 안내 ("9월 1-1주차 학습지가 준비됐어요") | 주차 라벨(exam.js calLabelFor) + 편지함 주간 봉투 |

| 정체 감지·보강 권유 | 유형별 정답률 추적(이미 있음) |

## 2. 채널 선택

- **알림톡(카카오 비즈메시지)** — 정보성 메시지 전용. 필요: 사업자등록 + 카카오톡
  채널 + 발신프로필 등록 + 공식 대행사(솔라피·알리고·NHN Cloud 등) API 계약.
  **템플릿 사전 심사제**(변수 자리만 바꿀 수 있는 고정 문안). 단가 문자보다 저렴.
- **문자(SMS/LMS)** — 대행사 API + **발신번호 사전 등록**만 있으면 됨. 심사 없어
  문안 자유. 알림톡 실패 시 문자 폴백이 대행사들 표준 기능이라 보통 둘을 묶는다.
- 권장: **알림톡 우선 + 문자 폴백** (대행사 한 곳 계약으로 둘 다 해결).

## 3. 법적 요건 (구현 전 확인)

- 정보성(학습 리포트·학습지 안내)은 광고 동의는 불요하나 **개인정보(전화번호)
  수집·이용 동의**는 필요 — 수집 화면에 목적·보유기간 고지.
- 광고성(이벤트·신규 과정 홍보)을 섞으려면 별도 **광고 수신 동의** + "(광고)"
  표기 + 야간(21~08시) 전송 제한.
- 학생이 미성년자이므로 동의 주체는 **학부모** — 번호도 학부모 번호를 받는다.

## 4. 아키텍처 (우리 스택 기준)

앱은 GitHub Pages 정적 페이지라 발송은 서버 몫:
```
프로필(전화번호 등록, 동의) ─→ Supabase nm_contacts 테이블
                                   ↓ (매주 월 아침)
        Supabase Edge Function + pg_cron ─→ 대행사 API(알림톡→문자 폴백)
```
- **⚠️ 전화번호를 nm_profiles에 넣지 말 것** — nm_profiles는 anon select가 열려
  있다(이름으로 이어하기 기능). 전화번호는 **별도 nm_contacts 테이블**에:
  anon은 insert만 허용(등록), select/update 금지. 발송은 서비스 롤(Edge Function)만.
- 대행사 API 키는 Edge Function 시크릿에만 — git·클라이언트 금지.
- 발송 이력 테이블(nm_notify_log)로 중복 발송 방지 + 주당 1회 상한.

## 5. 앱 쪽 선행 작업 (구현 시작점)

1. 옷장 '아이디 등록' 카드 아래에 "📱 학부모 알림 받기" 카드 — 전화번호 입력 +
   동의 체크(고지 문구) → nm_contacts insert. 3언어.
2. 주간 메시지 본문 생성기를 **클라이언트와 무관하게** 쓸 수 있도록, 주차 라벨·
   이번 주 세션 계산을 순수 함수로 분리(Edge Function이 재사용).
3. 알림톡 템플릿 문안 3종 초안 작성 → 대행사 심사 제출 (심사 3~5일 소요).

## 7. 구현 현황 (2026-09-01 — 알리고 확정 후 1차 구축 완료)

원장 확인 "알리고 API가 가능해"에 따라 §4~5를 실제로 구축했다. **키만 넣으면
발송되는 상태**이며, 아직 아무것도 자동 발송되지 않는다.

### 만들어진 것
- **Supabase `nm_contacts`** — anon은 **동의 체크된 insert만** 가능(RLS with check),
  select는 grant 층에서 원천 차단(RLS 이전에 권한 자체가 없음). 검증: 동의 true
  insert 성공 · 동의 false 거부 · anon 열람 permission denied 3건 모두 확인.
- **Supabase `nm_notify_log`** — 발송 이력. `(phone, week_key, kind)` unique로
  같은 주 중복 발송이 DB 층에서 막힌다. anon 접근 전무.
- **Edge Function `weekly-notify`** (배포됨, v1) — nm_contacts(active·동의)를 돌며
  ①주 1회 상한 확인 ②nm_profiles.state의 `weeklyDigest`(현재 과정)와
  `roadCadence`로 문안 조립(주차 라벨은 앱 exam.js와 같은 규칙, KST)
  ③알리고 LMS 발송(`https://apis.aligo.in/send/`) ④로그 기록.
  `{"dry":true}`면 발송 없이 문안만 돌려준다(테스트용).
- **앱** — ①`S.weeklyDigest`: 현재 과정이 바뀔 때마다 프로필에 저장(발송 함수가
  읽는 값) ②옷장에 "📱 학부모 알림 받기" 카드: 번호+동의 체크 → nm_contacts
  등록, 로컬에는 마스킹된 번호(`010-****-0000`)만 남김. 3언어.

### 원장이 해야 할 것 (이 순서대로)
1. 알리고 콘솔에서 **API 키 발급** + **발신번호 등록**(통신서비스 이용증명원 필요).
2. Supabase 대시보드 → Edge Functions → Secrets에 4개 등록:
   `ALIGO_API_KEY` · `ALIGO_USER_ID` · `ALIGO_SENDER`(등록한 발신번호) ·
   `NOTIFY_TRIGGER_KEY`(아무 긴 무작위 문자열 — 호출 암호).
3. **드라이런**(발송 없이 문안 확인):
   ```
   curl -X POST https://fgahqumaldheqettmvqg.supabase.co/functions/v1/weekly-notify \
     -H "Authorization: Bearer (anon key)" -H "Content-Type: application/json" \
     -d '{"trigger_key":"(NOTIFY_TRIGGER_KEY 값)","dry":true}'
   ```
4. 본인 번호로 옷장에서 등록 → dry 빼고 한 번 호출 → 실수신 확인.
5. 매주 자동화(월 08:00 KST): Supabase SQL로 pg_cron+pg_net 등록 —
   ```sql
   select cron.schedule('weekly-notify','0 23 * * 0', -- 일 23:00 UTC = 월 08:00 KST
     $$select net.http_post(
       url:='https://fgahqumaldheqettmvqg.supabase.co/functions/v1/weekly-notify',
       headers:=jsonb_build_object('Authorization','Bearer (anon key)','Content-Type','application/json'),
       body:=jsonb_build_object('trigger_key','(NOTIFY_TRIGGER_KEY 값)'))$$);
   ```
   (pg_cron·pg_net 확장이 꺼져 있으면 Dashboard→Database→Extensions에서 켠다)

### 주의
- 이 저장소·클라이언트에는 알리고 키를 절대 넣지 않는다(시크릿 전용).
- 알림톡으로 올리려면(단가↓) 카카오톡 채널·템플릿 심사 후 Edge Function의
  발송부만 알리고 알림톡 API(`kakaoapi.aligo.in`)로 바꾸면 된다 — 나머지
  파이프라인(연락처·상한·요약)은 그대로.
- 문자 문안을 바꾸려면 Edge Function `composeMsg()`만 수정해 재배포.

## 8. 릴레이 발송 (2026-09-05 — 원장: "내 사설서버(85.238.241.138)에 알리고가 붙어 있고, 리포트에도 이미 연결·API키 등록됨")

알리고는 **호출 IP 화이트리스트**를 검사한다. Supabase Edge Function은 고정 IP가 없어 알리고를
직접 부르면 막히므로, **이미 알리고에 등록된 쪽을 거친다.** 키는 그쪽에만 있고 Supabase에는 넣지 않는다.
(처음 메모의 34.22.104.117은 원장이 85.238.241.138로 정정함.)

소스: `supabase/functions/weekly-notify/index.ts` (저장소 루트). **v5 배포 완료(2026-09-05, 원장 "A 해봐 … 네가 넣어" 승인)**.

### 8-0. 시크릿은 Vault에 (2026-09-05)
Edge Secrets 대시보드는 원장이 직접 넣어야 해서, 대신 **Supabase Vault**에 넣었다(`vault.create_secret`). 함수는
환경변수 → Vault 순서로 읽는다(`secret()` 헬퍼 → `public.nm_notify_secret(p_name)` RPC, `security definer`,
**service_role만 execute** — anon/authenticated는 revoke). 지금 Vault에 있는 것: `NOTIFY_RELAY_URL`(Apps Script URL),
`NOTIFY_TRIGGER_KEY`(24바이트 난수). 값 확인·교체는 SQL 편집기에서
`select name from vault.secrets` / `select vault.update_secret(id, '새값')`.

### 8-0-1. 이 세션에서 호출하는 법
이 작업 환경은 `*.supabase.co`·`script.google.com`으로 나가는 curl이 막혀 있다. 대신 **DB 안에서 pg_net**으로
함수를 부른다(pg_cron 등록 때도 같은 문장을 쓴다):
```sql
select net.http_post(
  url := 'https://fgahqumaldheqettmvqg.supabase.co/functions/v1/weekly-notify',
  headers := jsonb_build_object('Content-Type','application/json','Authorization','Bearer <anon key>'),
  body := jsonb_build_object('trigger_key',(select decrypted_secret from vault.decrypted_secrets where name='NOTIFY_TRIGGER_KEY'),'probe',true));
-- 몇 초 뒤
select status_code, content from net._http_response order by id desc limit 1;
```
`probe:true`는 릴레이에 `{action:'ping'}`만 보내 응답 원문을 돌려준다(문자 없음).

### 8-0-2. 확인 결과 (2026-09-05)
- probe → Apps Script가 200으로 `{"result":"error","error":"Unknown action: ping"}` 응답. **연결·계약 OK.**
- 같은 방식으로 `{action:'aligo_sms', receiver:''}`를 보내니 **`Unknown action: aligo_sms`**. 즉 배포된 Apps Script에는
  문자 분기가 **없다** — git의 Code.gs와 같은 상태. 리포트 콘솔의 "문자 발송" 버튼도 이 URL로는 실제로 나가지
  않는다(눌러 보면 "❌ 전송 실패: Unknown action: aligo_sms"가 떠야 정상). → **경로 A는 현재 불가. 경로 B로.**

### 8-1. 경로 A — gfield-report의 Apps Script 웹앱 재사용 (권장: 새 코드 0줄)
gfield-report 콘솔의 "문자 발송"은 브라우저 → Apps Script 웹앱 → 알리고다. 계약(`index.html` `sendAligoSms`):
```
POST <Apps Script 웹앱 URL>   body {action:'aligo_sms', receiver:'010…', msg:'…', targetDate:''}
→ {result:'success'} | {result:'error', error:'…'}
```
- `weekly-notify` v4는 `NOTIFY_RELAY_URL`이 `script.google.com` 주소면 **이 계약으로 보낸다**.
  제목·msg_type은 계약에 없으므로 Apps Script 쪽이 정한다(본문이 90바이트를 넘으니 그쪽이 LMS로 보내야 한다 — 확인 필요).
- 필요한 것: Supabase Secrets에 `NOTIFY_RELAY_URL` = 콘솔 설정(API 키 및 환경 설정 → GOOGLE APPS SCRIPT URL)에
  저장된 바로 그 URL. **채팅에 붙이지 말고 Supabase 대시보드에서 직접 입력.**
- ⚠️ git의 `gfield-report/Code.gs`(마지막 커밋 3c3b80e) `doPost`에는 `aligo_sms` 분기가 **없다**(Unknown action).
  콘솔에서 문자가 실제로 나간다면 배포된 스크립트가 git 사본보다 새 것이다. 배포본에 분기가 있는지
  Apps Script 편집기에서 한 번 확인할 것. 없으면 경로 B.

### 8-2. 경로 B — 사설서버 85.238.241.138 에 릴레이 (현재 채택, 2026-09-05)
```
weekly-notify(Supabase) ──POST JSON──▶ 85.238.241.138:8090 /notify/send (relay.js) ──▶ apis.aligo.in
```
- `NOTIFY_RELAY_URL`이 Apps Script 주소가 아니면 이 계약으로 보낸다.
- Vault에 이미 넣어 둔 것: `NOTIFY_RELAY_URL` = `http://85.238.241.138:8090/notify/send`, `NOTIFY_RELAY_KEY`(난수).
  포트를 바꾸면 URL도 `vault.update_secret`으로 바꿀 것.
- **서버 쪽은 파일 하나로 끝난다**: `number_magic/scripts/notify-relay/relay.js`(Node 18+, 의존성 0).
  같은 폴더의 `relay.service`(systemd)·`relay.env.example` 참조. 알리고 API 키·아이디·발신번호는 서버의
  `relay.env`에만 둔다. `ALIGO_TESTMODE=Y`로 먼저 띄워 응답만 보고, 실수신 확인 뒤 `N`.
- 방화벽/보안그룹에서 **8090 인바운드**를 열어야 한다. 2026-09-05 pg_net으로 80·443·8080·3000을 두드려 봤을 때
  전부 TCP 타임아웃 — 지금은 밖에서 아무 포트도 안 열려 있다.
- 릴레이는 키 검사 + 시간당 상한(`MAX_PER_HOUR`, 기본 200) + 수신번호 형식 검사만 한다. 본문은 로그에 남기지 않는다.

**덤 — 리포트 콘솔 문자 버튼도 살리려면**: Apps Script `doPost`에 분기 하나 추가해 같은 릴레이로 넘긴다
(Script Properties에 `NOTIFY_RELAY_URL`, `NOTIFY_RELAY_KEY` 저장).
```js
else if (action === 'aligo_sms') data = aligoViaRelay_(payload);
// …
function aligoViaRelay_(p) {
  const props = PropertiesService.getScriptProperties();
  const r = UrlFetchApp.fetch(props.getProperty('NOTIFY_RELAY_URL'), {
    method: 'post', contentType: 'application/json', muteHttpExceptions: true,
    headers: { 'X-Relay-Key': props.getProperty('NOTIFY_RELAY_KEY') },
    payload: JSON.stringify({ receiver: String(p.receiver||'').replace(/\D/g,''), msg: p.msg || '', msg_type: 'LMS' })
  });
  const j = JSON.parse(r.getContentText() || '{}');
  if (!j.ok) throw new Error('relay: ' + JSON.stringify(j.detail || j));
  return { sent: true };
}
```
(콘솔이 보내는 `targetDate` 예약 발송은 알리고 `rdate/rtime` 필드가 필요해 릴레이에 아직 없다 — 필요하면 추가.)

### 8-3. 경로 C — DB 고정 IP로 알리고 직접 (2026-09-05, **현재 기본**)
알리고 키·아이디·발신번호를 원장이 채팅으로 줘서 **Vault**에 넣었다(`ALIGO_API_KEY`·`ALIGO_USER_ID`·`ALIGO_SENDER`).
Edge Function에서 직접 부르면 `인증오류입니다.-IP`(-101) — 함수의 외부 IP가 호출마다 바뀐다(54.180.141.19 →
13.209.98.43). 반면 **DB의 pg_net 외부 IP는 54.116.72.251로 고정**(3회 확인)이고, 알리고가 `/remain/`에 GET 쿼리를
받는 것도 확인했다(키를 쿼리로 줬을 때 오류가 "키 미입력"이 아니라 "-IP"로 바뀜).
- `public.nm_aligo_send(p_endpoint, p_query)` — Vault의 키·아이디·발신번호를 붙여 `net.http_get('https://apis.aligo.in/<endpoint>/?…')`.
  `public.nm_aligo_result(id)` — `net._http_response` 폴링. 둘 다 security definer, **service_role만 execute**.
- weekly-notify v7: `NOTIFY_RELAY_URL`이 없으면 이 RPC로 보낸다(`via:'aligo-db'`). 문안은 함수가 만들고 URL 인코딩도
  함수가 한다(`URLSearchParams`). `probe:'aligo'`는 같은 길로 `/remain/`만 부른다.
- **비동기 큐잉(v9)**: 함수는 `nm_aligo_send`로 pg_net 큐에 넣고 `request_id`만 `nm_notify_log`에 남긴 채 즉시 반환
  (`ok` NULL = 대기). pg_cron `nm-notify-reconcile`(2분마다, SQL만)이 `net._http_response`를 보고 `ok`·`result_code`·
  `detail`을 채운다. 함수 시작 때도 한 번 돌린다. **동기 폴링(v7·v8)은 안 된다**: pg_cron→pg_net→함수→pg_net 구조에서
  pg_net 워커는 배치 단위로 돌아 앞 배치(함수 호출)가 끝나야 뒤 요청(알리고)을 꺼내는데, 함수는 알리고 응답을 기다리니
  서로 기다린다(request 29↔30으로 확인).

### 경로 B 릴레이 계약
요청 `POST {receiver, msg, title, msg_type:'LMS'}` + 헤더 `X-Relay-Key`. 응답 JSON `{ok:true|false, detail?}`.

### 경로 B 사설서버 쪽 코드 (둘 중 서버 스택에 맞는 것 하나)

**Node (Express)** — 기존 리포트 서버에 라우트 하나 추가:
```js
// RELAY_KEY, ALIGO_API_KEY, ALIGO_USER_ID, ALIGO_SENDER 는 환경변수
app.post('/notify/send', express.json(), async (req, res) => {
  if (req.get('X-Relay-Key') !== process.env.RELAY_KEY) return res.status(403).json({ ok:false, detail:'bad key' });
  const { receiver, msg, title, msg_type } = req.body || {};
  if (!/^01\d{8,9}$/.test(String(receiver||''))) return res.status(400).json({ ok:false, detail:'bad receiver' });
  const form = new URLSearchParams({ key: process.env.ALIGO_API_KEY, user_id: process.env.ALIGO_USER_ID,
    sender: process.env.ALIGO_SENDER, receiver, msg: String(msg||''), msg_type: msg_type||'LMS', title: String(title||'') });
  const r = await fetch('https://apis.aligo.in/send/', { method:'POST', body: form });
  const j = await r.json();
  res.json({ ok: String(j.result_code) === '1', detail: j });
});
```

**Python (Flask)**:
```python
@app.post('/notify/send')
def notify_send():
    if request.headers.get('X-Relay-Key') != os.environ['RELAY_KEY']:
        return jsonify(ok=False, detail='bad key'), 403
    b = request.get_json(force=True) or {}
    if not re.fullmatch(r'01\d{8,9}', str(b.get('receiver',''))):
        return jsonify(ok=False, detail='bad receiver'), 400
    r = requests.post('https://apis.aligo.in/send/', data={

        'sender': os.environ['ALIGO_SENDER'], 'receiver': b['receiver'], 'msg': b.get('msg',''),
        'msg_type': b.get('msg_type','LMS'), 'title': b.get('title','')}, timeout=15).json()
    return jsonify(ok=str(r.get('result_code'))=='1', detail=r)
```
